## 功能

### 用眼架那套"按价格对账"优化净资产（2026-10-08 记）

眼架的做法是：这一包花掉的钱减去看得见的资产增加，剩下的部分去对真眼价格的整数倍，
对上了就认定钱变成了眼架里的存货（见 [design/networth.md](design/networth.md) 的眼架一节）。
想看这个思路能不能推广：**信使在路上的东西**、储藏处到身上的交接，现在靠时间窗和猜测，
能不能改成"花掉的钱对得上哪件东西的价格"。

做之前过一遍 [design/networth.md](design/networth.md) 里启发式规则的证据表：
每条新判据都要单独关掉逐次算账，真阳性少的不进正式代码。
价格对账最怕的是**巧合**——几百块的差额能凑上的组合很多，门槛要从价格分布上定，不能事后凑。

### 净资产的三处疑点（2026-10-15 代码审核记，(c) 已处理）

代码审核看出来的，**都还没用录制证实**，所以只记评估办法、不改 `ui/js/networth.js`。按
[design/networth.md](design/networth.md) 的规矩：每条都要单独开关、在录制上逐次算账，
看帮忙和帮倒忙各几次，不看总数。复算用 [dev-tools.md「离线复算」](design/dev-tools.md#离线复算)那套
（Node 直接 import 真实的 `cachepool.js` + `networth.js`），播给人看用 `tools/replay.py`。
下面说的"现有录制"是开发机 `records/` 下那 17 份（m8988783173 ~ m9044675249）。

**(a) 同一个 matchid 里重开一局，时钟倒流重置不触发**（`update()` 开头，约 653 行）

- 疑点：重置只认 `clock >= 0` 时的倒流。若练习 / 机器人局重开后 matchid 不变，新的一局先从负数数起，
  `lastClock` 跟着变成负数，号角之后时钟一路往上走，**倒流条件一次都不成立**——`dispenserValue`、`dispenserGone`、
  `proxy`、`giftGiven`、`seenVariants` 等带到新的一局。
- 先查前提：现有 17 份录制全是正式对局，每份只有一个 matchid，`clock >= 0` 之后的倒流**一次都没有**，
  所以这条在现有语料里测不出来。要**新录一份**：机器人 / 练习局打过 0:00 后重开，看 matchid 变没变。
  变了的话 `main.js` 的 `newMatch` 已经整份重置，这条不用改。
- 若 matchid 不变，候选修法是"从 `>= 某值` 掉到负数也算重置"。门槛不能是 0：17 份里有 15 份号角前出现过
  `0 → -59`、`0 → -44` 这样的跳变（选人 / 策略阶段时钟先归零再倒数），一共 31 次；
  另有 m9006189153 一次 `135 → -10`（看回放时拖了进度）。门槛取 60 之类，在这 17 份上应当只命中后者——
  要逐份确认**只命中**它，并对比 m9006189153 那次重置前后十人净资产与官方值的差。

**(b) 眼架判据拿的是资产净变化，同一包一减一增会抵消**（传给 `noteDispenser` 的 `assetUp`，约 671 行）

- 疑点：`assetUp = 装备栏变化 + 储藏处变化 + 传送槽变化`，是**带符号的和**。同一包里用掉一张 TP（−100）
  又买了一件 100 金的东西进装备栏（+100），`assetUp = 0`，而付出的 100 恰好是两个真眼的价——
  被认成"两个真眼进了架子"。networth.md 说挡误判的是"资产没多"，按这个意思应只取**各项的正增量**之和。
- 评估：把 `assetUp` 换成 `max(0, Δslot) + max(0, Δstash) + max(0, ΔTP)` 做成开关，17 份录制逐份复算。
  只看**持有眼架期间**的包：两种算法给出的 `assetUp` 不同、且结果导致 `dispenserValue` 不同的那几次，
  逐次对官方净资产，看改后是帮忙还是帮倒忙。另一侧要盯住：取正增量后，"卖掉一件 + 同包买眼"这类
  本来靠负数抵消掉的包会不会被第二个分支（`spare = paid − assetUp`）多认。

**(c) ~~宝石手递手那一包恰好有大额进账，这颗宝石整局不计~~**：2026-10-16 去掉了那道豁免（宝石卖不掉，用户确认；
二十份录制里宝石离开物品栏 19 次，豁免一次都没触发过）。见 `networth.js` 的 `noteProxy`。

### 无感更新（2026-10-15 记）

现在的一键更新要用户自己点：启动时查到新版 → 设置卡片里出现 `NEW` → 点「立即更新」→ 下载、验签、
弹出 NSIS 的进度窗口（`installMode: passive`）→ 装完自动重启。想做到**不用点、不打扰**。用户有参考项目，做之前先看它怎么做的。

要想清楚的：

- **什么时候装**：绝不能在对局中——装的时候程序要退出，覆盖层会消失。候选：后台下载好，等到
  **不在对局中**（主菜单、Dota 没开）或**程序退出时 / 下次启动时**再装
- **装的时候弹不弹窗**：`installMode` 换成 `quiet` 就没有进度窗口；但 quiet 装失败了用户完全不知道，要有兜底（日志 + 卡片里提示）
- **要不要让用户关掉**：设置里加一个"自动更新"开关？默认开还是关
- **绿色版做不到**：zip 版没有安装器，一键更新本来就只对安装版生效（`updater.rs` 的 `app_installed`），绿色版维持现状（打开下载页）

## 开发向

### 已知限制：收包线程能被一个停住的连接卡住（2026-10-15 代码审核记，先不修）

`gsi.rs` 用 tiny_http 收包，**body 是在收包线程里读的**，而 tiny_http 不暴露 socket 的读超时。
一个连接报了 Content-Length、发到一半停住，线程就一直等在那里，之后 Dota 的包全进不来。
2026-10-15 加的 4MB 上限只挡得住"报得太大"，挡不住"停住不发"。

触发条件是**本机某个进程主动连 53000 并停住**——Dota 不会这样（它每包都是一次性发完的）。
所以眼下不值得为它动收包这一层。

将来要修的话，优先**换成 std 的 `TcpListener` + `set_read_timeout`，自己解析 GSI 的 POST**：
Dota 发来的只有"请求行 + 头 + Content-Length 定长 body"这一种形状，自己读几十行就够，
顺便去掉 tiny_http 依赖。不要在 tiny_http 外面再套线程池之类绕过去。

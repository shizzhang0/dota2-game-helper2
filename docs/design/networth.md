# 净资产口径与价格源

参考 [nocamles/dota2_amount_plugins](https://github.com/nocamles/dota2_amount_plugins)，价格源与若干口径有改进。

> **口径已对照游戏回放的官方「财产总和」逐点验证。**
> 2026-09-02：开局 0:00 为 600（白送的 TP 不计）· 储藏处计入 · 信使在途计入 · 中立物品不计。
> 2026-09-07：快速模式 matchid 8986026437 取七个时间点全部吻合（见文末）。

```
净资产 = player.gold
       + Σ 装备栏/储藏处物品价格（slotN / stashN，消耗品按剩余充能折价）
       + 在途物品（被信使取走、尚未送达的部分）
       + 自己买的传送卷轴 × 100
       + 魔晶（hero.aghanims_shard）
       + 吞噬类永久 buff：
           神杖/祝福 modifier_item_ultimate_scepter_consumed
           月之碎片   modifier_item_moon_shard_consumed
```

GPM / XPM 直接用 `player.gpm` / `player.xpm` 现成字段。

## 传送卷轴

**`teleport0` 整个槽位排除**（2026-09-01 实测定案）。开局白送一张，**阵亡时还会再送一张**。
三局数据里 TP 只出现在 `teleport0`（5811 次），从不落进普通格子或储藏处，按槽位排除是干净的。
参考实现 nocamles 的槽位表同样不含传送槽。

**但自己买的要算**（每张 100）。判据：**充能增加时人是活的**。
三局 15 次充能增加的归属：开局 2、阵亡赠送 11、购买 2——赠送全部发生在
`hero.alive === false` 的那一秒，与复活时刻无关；离复活 60~135 秒的两次增加确认是购买。

**用掉哪一张按先进先出**（2026-09-08 定案）。传送槽是个充能堆叠，用掉的那一张
本身没有身份，只能靠对账反推。两局共九个官方"财产总和"取点：

| 模型 | 旧局 8986026437 | 新局 8987649931 |
|---|---|---|
| 优先扣自购（早期实现） | 7/7 | **1/2** |
| 优先扣白送 | 7/7 | **1/2** |
| **先进先出** | **7/7** | **2/2** |

旧局三种模型打平——那局自购 TP 一直是 0，没有区分度；新局买了 5 张、白送 7 张、
用掉 9 张，才把它们分开。

早期实现是"优先扣自购"，理由写的是"买张 TP 立刻用掉是常见操作，宁可少算不虚高"。
结果就是**系统性少算**：新局末尾手里 3 张、其中 1 张是买的，却算成了 0，整整少 100。

> 2026-09-07 复核：旧局 5 次充能增加**金钱一次都没掉**（Δ 为 0 或 +2 的被动收入），
> 确认全是赠送，"充能增加时人是活的 = 自己买的"这条判据成立。

> 队列和实际充能对不上时（漏包）以实际为准，补进来的一律算白送——宁可少算。

## 物品

- **消耗品按剩余充能折价**：`价格 × 当前充能 ÷ 满充能`。判据是 OpenDota 的
  `qual == "consumable"`——瓶子有充能但不是消耗品，空瓶仍值全价 675。
- **中立物品不计**（`neutralN` / `preserved_neutralN`）：OpenDota 表里价格本来就是 0。
- **队友塞的东西不计**：`items[].purchaser` 标明谁买的。队友让你代拿的圣剑（5600）、
  宝石（900）不该算进自己的资产；自己买的、无主的（`purchaser = -1`，如 famango）、
  从敌人手里缴获的都算。

  **`purchaser` 是全局 0-9 槽位（天辉 0-4 / 夜魇 5-9），不是 `team_slot`**——
  实测夜魇局 `team_slot=2` 而 `purchaser=7`。按 `team_slot` 直接比会让夜魇局所有自己的
  装备被判成别人的，净资产塌成只剩金钱，而且天辉局测不出来。
  正确公式：`purchaser == team_slot + (team_name == "dire" ? 5 : 0)`，
  与 `CHAT_MESSAGE_BUYBACK` 的 `playerid1` 是同一套编号。
  （上游 nocamles 的 issue #1 把它描述成对应 `team_slot`，是个坑。）
  实现上槽位算错会退化成"全都算"，即原行为，不会错误清空资产。

- **items 段是全量推送**：实测对局中每包都含完整 23 个槽位，从不缺席或为空，
  所以缓存池整段替换是安全的（参考实现按槽位逐个合并，属多余防御）。
  但**号角前会推空 `items`，缓存池必须拒绝用空对象覆盖已有数据**。

## 在途物品

物品被信使取走后、送达前，既不在装备栏也不在储藏处，**GSI 完全看不见它**。
实测每局造成 1~10 次凹陷，幅度 1000~5000，持续中位 6~29 秒。

做法：储藏处减少而装备栏没有相应增加时，把差额记进在途账；等它送达或超时（90 秒）再抹掉。

**已知误差**：从储藏处直接卖东西会让净资产虚高最多 90 秒（这个操作很少见）。

## 吞噬类 buff

**一律计入**，不管自己买的、肉山掉的，还是炼金术士送的——吞下去就是永久属性，到手即归自己。
这点和"队友让你代拿的物品"不同：那个随时能还回去，所以不计。
`permanent_buffs` 里也确实没有 `purchaser` 字段。

**神杖系的真实机制**（别按"吞掉物品"去理解）：

| 情形 | 物品栏表现 | 计价 |
|---|---|---|
| 阿哈利姆神杖 `ultimate_scepter` | **当物品拿着**，本身不变 buff | 4200，按物品价 |
| 神杖 + 祝福卷轴 `recipe_ultimate_scepter_2`（1600） | 两件**自动合成为 buff**，同时从物品栏消失 | 5800（阿哈利姆祝福） |
| 炼金术士送神杖给队友 | 受赠方**直接得到 buff**，物品栏里从没出现过东西 | 4200（一根神杖） |
| 肉山掉的祝福 | 当物品捡起来，消耗后只剩 buff | 5800 |

> 查神杖价用的 key 是 `ultimate_scepter`，**别用 `ultimate_scepter_2`**——
> 那是 5800 的阿哈利姆祝福，用错会让常见情况高估 1600。

两种来源共用 `modifier_item_ultimate_scepter_consumed` 一个名字，光看 buff 分不出档次，
所以靠**物品栏历史**判断：见过祝福卷轴 / 祝福成品 / 肉山祝福 → 5800；都没见过 → 4200。
若某版本给祝福单独的 buff 名（`modifier_item_ultimate_scepter_2_consumed`）也直接认。

实测（dump 8975953942 局）：clock=1838 神杖在 slot3 → 1845 祝福卷轴进 stash →
1852 两件同时消失、buff 出现、腾出一个格子。全量扫描确认**神杖系物品与该 buff 从未同时存在**，
不会重复计价。

> 注意 `refresher_shard` 是 1000，别和祝福卷轴的 1600 混。

### 两个踩过的坑

- **buff 出现时要冲销在途账**：物品被合成/吞噬时从物品栏凭空消失，长得和"被信使取走"
  一模一样。不冲销的话这部分价值会既算进 buff、又挂在在途账上，重复计到 90 秒超时。
  实测该局合成瞬间原本会从 30127 跳到 35949，冲销后平滑为 30127 → 30149 → 30121。
- **物品栏历史只能决定价格档次，不能当作 buff 已生效的依据**：否则卷轴还在包里、
  buff 尚未出现时，物品价和 buff 价会同时计入（曾导致买一件 1600 的卷轴让净资产跳涨 5800+）。

## 价格源

**价格表是本地常数，程序运行时不联网。**

`constants/item_prices.json` 走和其他常数表同一套：播种到配置目录、缺键自动补齐、
改 JSON 重启生效。只保留 cost / consumable / charges 三个字段（362KB → 15KB）。
神杖 / 魔晶 / 月碎的价格优先查表，查不到才退回常数表。

**更新方式**：跑 `python tools/fetch_prices.py` 重新生成，提交，重新构建。
价格只随游戏版本变，本来就该跟着版本走。

### 为什么不在运行时拉

原先每次启动都后台拉一次 OpenDota，写盘做缓存。两个问题，第一个是真 bug：

1. **写盘时只留了 `cost`**，把 `consumable` 和 `charges` 丢了——而消耗品按剩余充能
   折价正靠这两个字段。于是**联网成功一次，折价就静默失效**，全部按全价算。
   更糟的是缓存优先级高于内嵌快照，这个错会一直盖住对的那份。
   实测：内嵌快照里 39 件物品带 `charges`，缓存里 0 件。
2. **拉取是异步的**，而面板启动时就要价格表，所以首次进对局用的多半是上次的缓存，
   价格总滞后一次启动。

顺带去掉了 `reqwest` 依赖，程序也就真的一个网络请求都不发了。

### OpenDota 会落后于游戏版本

它仍是我们能拿到的最好的源——游戏自己的价格在 VPK 包里，要自己写解析且格式随版本变，不值得。
（这一条对"抓快照"和"运行时拉取"同样成立，换成本地常数并不改变价格本身的准确性。）

因此加一张本地覆盖表 `constants/item_price_overrides.json`（`物品名: 实际价格`，
下划线开头的键当注释跳过），在 `get_item_prices` 返回前套用。走"常数外置"同一套路子：
改 JSON 重启生效，不必重新编译。上游修好后删掉对应行即可——套用时若发现覆盖值与上游已经一致，
会写一条日志提示可以删。

已知需要覆盖的（2026-09-07 实测）：

| 物品 | OpenDota | 游戏实际 |
|---|---|---|
| 龙心 `heart` | 5100 | **5200** |

同一局里辉耀 4700 / 冰眼 5900 / 法师克星 3100 / 相位鞋 1400 / 影刃 3250 / 银月 5700 /
魔晶 1400 / 魔杖 460 / 掠夺者 2800 均验证正确，所以这是个例，不是整张表都偏。

## 对账方法

差额排查照这个做，**选点比多测几局更重要**：

1. 开录制，打完用回放看官方「财产总和」
2. **只选自己阵亡、且没有信使在途的时刻**——那时金钱只有 +2/秒被动收入，
   一两秒的对齐误差只有个位数
3. 信使送达前后、补刀密集的时刻**两秒就能差 100 以上**，没有分辨力，别在那里取点
4. 复算时直接 import 真实的 `ui/js/networth.js`，不要另写一份，否则测的是复制品

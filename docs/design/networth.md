# 净资产口径与价格源

参考 [nocamles/dota2_amount_plugins](https://github.com/nocamles/dota2_amount_plugins)，价格源与若干口径有改进。

> **口径已对照游戏回放的官方「财产总和」逐点验证。**
> 2026-09-02：开局 0:00 为 600（白送的 TP 不计）· 储藏处计入 · 信使在途计入 · 中立物品不计。
> 2026-09-07：快速模式 matchid 8986026437 取七个时间点全部吻合（见文末）。
> 2026-09-08：快速模式 matchid 8988706327 取六个时间点全部吻合
> （1942 / 3082 / 25192 / 27050 / 27336 / 30504，最后一个是末局值）。
> 这一轮挖出并修掉了三个 bug：消耗品叠加只算一份、眼架按固定价 50、传送卷轴扣错张。

```
净资产 = player.gold
       + Σ 装备栏/储藏处物品价格（slotN / stashN，消耗品按剩余充能折价）
       + 在途物品（被信使取走、尚未送达的部分）
       + 自己买的传送卷轴 × 100
       + 眼架里装的眼（GSI 不给内容，靠购买事件与插眼位置推）
       + 魔晶（hero.aghanims_shard）
       + 吞噬类永久 buff：
           神杖/祝福 modifier_item_ultimate_scepter_consumed
           月之碎片   modifier_item_moon_shard_consumed
```

GPM / XPM 直接用 `player.gpm` / `player.xpm` 现成字段。

## 传送卷轴

**`teleport0` 整个槽位排除**（2026-09-01 实测定案）。开局白送一张，**阵亡时还会再送一张**。
三局数据里 TP 只出现在 `teleport0`（5811 次），从不落进普通格子或储藏处，按槽位排除是干净的。
参考实现 nocamles 的槽位表同样不含传送槽。

**但自己买的要算**（每张 100）。判据：**充能增加时人是活的**。
三局 15 次充能增加的归属：开局 2、阵亡赠送 11、购买 2——赠送全部发生在
`hero.alive === false` 的那一秒，与复活时刻无关；离复活 60~135 秒的两次增加确认是购买。

**用掉的先扣白送那张**（2026-09-08 二次定案）。传送槽是个充能堆叠，用掉的那一张
本身没有身份，只能靠对账反推。

判据来自 8988706327：**全局只买过一张 TP**（clock 721），而官方净资产从那一刻起
**一直算着这 100**，中间用掉过四张也没掉。只有"先扣白送"能产生这个行为——
先进先出会在第二次用掉时就把它扣没。六个取点里"先扣白送"全中，先进先出中三个。

> **这条推翻了同一天早些时候的结论，理由要写清楚。** 当时依据是另一局两个取点里
> 先进先出 2/2、其余模型 1/2，于是选了先进先出。但**那次测量时还带着两个 bug**：
> 消耗品叠加只算一份（一叠两个烟少 50）、眼架一律按 50（少 100~150）。
> 两者都在 100 量级，足以把那一个取点判反。现在两个 bug 都修了，
> 结论跟着翻过来——**用带 bug 的实现比模型，比出来的是 bug 的形状。**

> 2026-09-07 复核：旧局 5 次充能增加**金钱一次都没掉**（Δ 为 0 或 +2 的被动收入），
> 确认全是赠送，"充能增加时人是活的 = 自己买的"这条判据成立。

> 队列和实际充能对不上时（漏包）以实际为准，补进来的一律算白送——宁可少算。

## 物品

- **消耗品按充能数折算**：`价格 × 当前充能 ÷ 满充能`。判据是游戏文件里的
  `ItemQuality == "consumable"`（落到价格表里是 `consumable` 字段）——瓶子有充能但不是
  消耗品，空瓶仍值全价 675。

  同一个公式管两件事：**用剩的**（吃树 1/3 → 30）和**叠起来的**（烟 ×2 → 100）。
  表里的 `charges` 是"一份卖几个充能"，物品栏里的是当前实际数量，两者相除就是份数。
  **所以不能给它设上限。** 早期写了 `charges <= max` 才折算、超过就退回单份价格，
  于是一叠两个烟只算 50——2026-09-08 实测官方净资产正好比我们多这 50。
  真眼、诡计之雾、吃树、净化都是这种能叠的消耗品。

  > 表里没有 `charges` 的消耗品（树苗、芒果、仙灵之火）走不到这个公式，一律按全价算。
  > 原先这里举的例子是"树苗 1/4 → 23"，而树苗在表里从来没有 `charges`
  > （换成游戏文件之前也没有），那个数算不出来——例子换成真能对上的吃树。

### 眼架：GSI 的一个盲区

真眼假眼会叠在一起变成 `ward_dispenser`，而 **GSI 对它永远只给 `charges: 1`**，
装了几个眼、什么眼，一个字都不说。按表里的固定价 50 算是错的——
实测一局：22:47 买三个真眼合成眼架（150 金），26:27 又补一个（200 金）。

能观测到的只有两件事，于是就靠这两件事推：

| 事件 | 怎么看见 |
|---|---|
| 合成 | 散装的眼从物品栏消失、眼架出现的那一包，把价值平移进去 |
| 拿着眼架再买眼 | 物品栏毫无变化，只能靠 `CHAT_MESSAGE_ITEM_PURCHASE` 事件 |
| 插眼 | minimap 上多一个我方真眼，**且在自己英雄 700 距离内** |

> **购买事件必须每包都消费掉**，哪怕当时没有眼架。只在有眼架时才读的话，
> "合成之前买的那几个眼"会一直留在未处理集合里，等眼架一出现被重新算一遍——
> 价值既随物品平移进来、又被事件加一次，正好翻倍。（实测眼架涨到过一万多。）

> **距离归属是必需的。** minimap 的眼条目只有 `team`、没有玩家 id，也没有"插眼"事件；
> 不按距离过滤，队友插的真眼会把我们的库存扣光。真眼施法距离 500，取 700 留余量。

> **眼架会短暂消失**：被信使拿着的十几秒里 GSI 完全看不见它（实测一次 10 秒）。
> 立刻清零就把刚合成的价值丢了，所以给 20 秒宽限。真用完了，插眼扣减本来也已经扣到 0。

**残留误差**：眼插得离自己很远（比如用信使送眼、或被顶到位移技能带走）会漏扣；
队友恰好在自己身边插真眼会多扣。幅度都是 50 的整数倍，且眼架一空就归零、不跨局累积。
假眼不用管，它本来就不要钱（0 金）。
- **中立物品不计**（`neutralN` / `preserved_neutralN` 是 GSI 的槽位名，整个槽位直接跳过）：
  它们在价格表里本来也是 0——扫帚柄、海洋之心、顶点这些逐个查过，游戏文件写的就是 0。
- **队友塞的东西不计**：`items[].purchaser` 标明谁买的。队友让你代拿的圣剑（5600）、
  宝石（900）不该算进自己的资产；自己买的、无主的（`purchaser = -1`，如 famango）、
  从敌人手里缴获的都算。

  **`purchaser` 是全局 0-9 槽位（天辉 0-4 / 夜魇 5-9），不是 `team_slot`**——
  实测夜魇局 `team_slot=2` 而 `purchaser=7`。按 `team_slot` 直接比会让夜魇局所有自己的
  装备被判成别人的，净资产塌成只剩金钱，而且天辉局测不出来。
  正确公式：`purchaser == team_slot + (team_name == "dire" ? 5 : 0)`，
  与 `CHAT_MESSAGE_BUYBACK` 的 `playerid1` 是同一套编号。
  （上游 nocamles 的 issue #1 把它描述成对应 `team_slot`，是个坑。）
  实现上槽位算错会退化成"全都算"，即原行为，不会错误清空资产。

- **items 段是全量推送**：实测对局中每包都含完整 23 个槽位，从不缺席或为空，
  所以缓存池整段替换是安全的（参考实现按槽位逐个合并，属多余防御）。
  但**号角前会推空 `items`，缓存池必须拒绝用空对象覆盖已有数据**。

## 在途物品

物品被信使取走后、送达前，既不在装备栏也不在储藏处，**GSI 完全看不见它**。
实测每局造成 1~10 次凹陷，幅度 1000~5000，持续中位 6~29 秒。

做法：储藏处减少而装备栏没有相应增加时，把差额记进在途账；等它送达或超时（90 秒）再抹掉。

**已知误差**：从储藏处直接卖东西会让净资产虚高最多 90 秒（这个操作很少见）。

## 吞噬类 buff

**一律计入**，不管自己买的、肉山掉的，还是炼金术士送的——吞下去就是永久属性，到手即归自己。
这点和"队友让你代拿的物品"不同：那个随时能还回去，所以不计。
`permanent_buffs` 里也确实没有 `purchaser` 字段。

**神杖系的真实机制**（别按"吞掉物品"去理解）：

| 情形 | 物品栏表现 | 计价 |
|---|---|---|
| 阿哈利姆神杖 `ultimate_scepter` | **当物品拿着**，本身不变 buff | 4200，按物品价 |
| 神杖 + 祝福卷轴 `recipe_ultimate_scepter_2`（1600） | 两件**自动合成为 buff**，同时从物品栏消失 | 5800（阿哈利姆祝福） |
| 炼金术士送神杖给队友 | 受赠方**直接得到 buff**，物品栏里从没出现过东西 | 4200（一根神杖） |
| 肉山掉的祝福 | 当物品捡起来，消耗后只剩 buff | 5800 |

> 查神杖价用的 key 是 `ultimate_scepter`，**别用 `ultimate_scepter_2`**——
> 那是 5800 的阿哈利姆祝福，用错会让常见情况高估 1600。

两种来源共用 `modifier_item_ultimate_scepter_consumed` 一个名字，光看 buff 分不出档次，
所以靠**物品栏历史**判断：见过祝福卷轴 / 祝福成品 / 肉山祝福 → 5800；都没见过 → 4200。
若某版本给祝福单独的 buff 名（`modifier_item_ultimate_scepter_2_consumed`）也直接认。

实测（dump 8975953942 局）：clock=1838 神杖在 slot3 → 1845 祝福卷轴进 stash →
1852 两件同时消失、buff 出现、腾出一个格子。全量扫描确认**神杖系物品与该 buff 从未同时存在**，
不会重复计价。

> 注意 `refresher_shard` 是 1000，别和祝福卷轴的 1600 混。

### 两个踩过的坑

- **buff 出现时要冲销在途账**：物品被合成/吞噬时从物品栏凭空消失，长得和"被信使取走"
  一模一样。不冲销的话这部分价值会既算进 buff、又挂在在途账上，重复计到 90 秒超时。
  实测该局合成瞬间原本会从 30127 跳到 35949，冲销后平滑为 30127 → 30149 → 30121。
- **物品栏历史只能决定价格档次，不能当作 buff 已生效的依据**：否则卷轴还在包里、
  buff 尚未出现时，物品价和 buff 价会同时计入（曾导致买一件 1600 的卷轴让净资产跳涨 5800+）。

## 价格源

**价格表是本地常数。程序运行时不联网，也不读游戏文件。**

`constants/item_prices.json` 走和其他常数表同一套：播种到配置目录、缺键自动补齐、
改 JSON 重启生效。只保留 cost / id / consumable / charges 四个字段。
神杖 / 魔晶 / 月碎的价格优先查表，查不到才退回常数表。

**数据源是游戏本体自己的文件**，在开发机上解析、把结果作为快照提交：

| 取什么 | 从哪来 |
|---|---|
| 价格 | `scripts/npc/items.txt` 的 `ItemCost` |
| 物品 id | `scripts/npc/npc_ability_ids.txt`（购买事件只给 id，见眼架那节） |
| 消耗品判据 | `ItemQuality == "consumable"` |
| 满充能 | `ItemInitialCharges` |
| 对齐的版本号 | `resource/localization/patchnotes/patchnotes_english.txt` 里最新的补丁 |

四份文件都在 `game/dota/pak01_dir.vpk` 里，都是明文 KV。**更新方式**：跑
`python tools/sync_constants.py`，它重新生成价格表、更新 `constants/patch.json`
的版本号、并打印这一版相对上一版的差异；看完差异再提交、重新构建。

### 为什么从 OpenDota 换成游戏文件

原先快照取自 OpenDota `constants/items`。它会落后于游戏版本，且落后得没有规律。
2026-09-09 拿 7.41e 的游戏文件逐项对照当时提交的那份快照：

| | |
|---|---|
| 价格不一致 | **12 项** |
| 游戏有、OpenDota 没有 | **44 项**（几乎全是合成卷轴，在包里是有价值的） |
| OpenDota 有、游戏没有 | 1 项（`diffusal_blade_2`，已移除的物品） |
| id 不一致 | **0**（490 个共有物品全对） |
| consumable / charges | 完全一致（29 vs 29，逐项 charges 相同） |

差得最多的几项：

```
dagon_5       OD=7650  game=7400  (-250)
dagon_4       OD=6500  game=6300  (-200)
dagon_3       OD=5350  game=5200  (-150)
recipe_gungir  OD=400  game= 300  (-100)
heart         OD=5100  game=5200  (+100)
```

最后一行值得单独记：**龙心 5200 是我们靠官方「财产总和」逐点对账手工查出来的，
而游戏文件里写的就是 5200。** 反过来说，Dagon 五档全错，除非有人真出了 Dagon，
手工对账一辈子撞不上——**手工对账能证伪，不能枚举。**

因此源头换掉，同时删掉那张本地覆盖表 `item_price_overrides.json`：它存在的唯一理由
就是上游会落后。想手改单个价格的退路仍在——配置目录里的 `item_prices.json`
本来就盖过内嵌快照，直接改那一个文件就行。少一层就少一处对不上。

> **找不到 Dota、或 `items.txt` 哪天被编译成二进制格式，脚本一律硬失败，
> 绝不回退到 OpenDota。** 静默降级到更差的源正是下一节那个 bug 的形状。

### 为什么解析只在开发机上做

发布出去的 exe 里没有 VPK 解析，也不去找 Dota 的安装目录取价格。理由：

- 用户拿到的应当是**一份确定的常数**，而不是一个"结果取决于本机装了哪个版本"的程序。
  出了差额，我们要能知道他用的是哪一版价格表——`constants/patch.json` 就是为此存在。
- VPK 目录格式（v2）稳定，但 `items.txt` 会不会哪天变成编译格式不由我们决定。
  这个风险留在开发机上，最坏是脚本报错；放进运行时，最坏是用户的净资产静默归零。
- 程序至今只做两件与游戏目录有关的事：写 GSI 的 cfg、读 GSI 推来的数据。不加第三件。

### 版本戳

`constants/patch.json` 记一行「本项目的常数表对齐到哪个 Dota 版本」：

```json
{ "dota": "7.41e", "synced": "2026-09-09" }
```

它也会落到配置目录，但**每次启动无条件覆盖**，不走其他常数表那套"缺键即补"——
那套只补缺键、不改已有键，版本号会被永久钉在旧值上。而这个版本号必须准确，
因为程序靠它做一件事：

**盘上记的版本 ≠ 内嵌的版本时，`item_prices.json` 直接换成新表**，而不是补缺键。

这条是必须的，不是图省事。价格表原先靠覆盖表修正上游滞后；覆盖表删掉之后，
如果只补缺键，升级上来的用户盘上那份旧价格表会**继续盖住**内嵌的新表，
龙心悄悄退回 5100——比改这一版之前还差。代价是用户手改过的价格会在版本更新时
被覆盖，这是对的：那些手改本来就是在修一张过时的表。

时间表（`normal.json` 等）不在此列，它们是我们自己写的，用户的调整要留着。

一个戳管全部常数表，不是每张表一个。价格随补丁变，`normal.json` / `turbo.json` /
`towers.json` 里的符点、肉山、塔防、堆野窗口同样随补丁变，它们是一起对齐的。

### 补丁来了要做什么

价格是脚本自动的，计时不是——`items.txt` 里没有符刷新间隔。所以两条路都走，
而且都在同一个 VPK 里：

1. **价格 / id**：脚本重新生成，看差异，提交。不需要判断。
2. **计时常数**：脚本顺手从 `patchnotes_english.txt` 里筛出这一版命中
   符 / 肉山 / 塔 / 战鼓 / 买活 / 莲花 / 智慧 / 赏金 / 野怪 / 信使 / 折磨兽
   这些关键词的条目，人读一遍，决定要不要动那三张表。

实测 7.41e 共 161 条更新日志，命中上述关键词的只有一条（折磨兽弹道），
也就是说那一版不必动计时表——**这个结论本身就是脚本该给出的东西**，
免得每次补丁都从头翻一遍日志。

### 为什么不在运行时拉

原先每次启动都后台拉一次 OpenDota，写盘做缓存。两个问题，第一个是真 bug：

1. **写盘时只留了 `cost`**，把 `consumable` 和 `charges` 丢了——而消耗品按剩余充能
   折价正靠这两个字段。于是**联网成功一次，折价就静默失效**，全部按全价算。
   更糟的是缓存优先级高于内嵌快照，这个错会一直盖住对的那份。
   实测：内嵌快照里 39 件物品带 `charges`，缓存里 0 件。
2. **拉取是异步的**，而面板启动时就要价格表，所以首次进对局用的多半是上次的缓存，
   价格总滞后一次启动。

顺带去掉了 `reqwest` 依赖，程序也就真的一个网络请求都不发了。

## 对账方法

差额排查照这个做，**选点比多测几局更重要**：

1. 开录制，打完用回放看官方「财产总和」
2. **只选自己阵亡、且没有信使在途的时刻**——那时金钱只有 +2/秒被动收入，
   一两秒的对齐误差只有个位数
3. 信使送达前后、补刀密集的时刻**两秒就能差 100 以上**，没有分辨力，别在那里取点
4. 复算时直接 import 真实的 `ui/js/networth.js`，不要另写一份，否则测的是复制品

2026-09-07 的验证记录（七点全中）：

| 时刻 | 官方 | 覆盖 heart 后 |
|---|---|---|

# 倒计时：神符 · 堆野 · 敌方塔防 · 敌方买活

面板上的时间类显示项。数据结论来自 3 局实测 dump（2 快速 + 1 正常，`../../../dota2_gsi_dump/dump/`）
与后续进游戏核对。

## 显示项

| 项目 | 数据源 | 规则 |
|---|---|---|
| 中路符时间线 | `map.clock_time` | 0:00 赏金 → 2:00、4:00 圣水符 → 6:00 起每 2 分钟强化符。一个显示位，图标随阶段变化 |
| 赏金符 | `map.clock_time` | 0:00 起每 3 分钟 |
| 智慧神符 | `map.clock_time` | 7:00 起每 7 分钟 |
| 莲花 | `map.clock_time` | 正常 3:00 起每 3 分钟；**快速 1:30 起每 90 秒** |
| 堆野窗口 | `map.clock_time` | 野怪每整分钟刷新，倒数到整分 |
| 敌方塔防 | events 解析 | ready / 冷却倒计时，含刷新里程碑 |
| 敌方买活 | events 解析 | 五个敌方槽位的买活冷却状态 |

倒计时是**纯函数**：常数表 + `clock_time` 算出全部结果，不维护自己的计时器，
因此暂停、跳变、中途启动都不需要特殊处理。

## 常数外置

`constants/normal.json` + `constants/turbo.json`：各事件的起始时间、周期、堆野窗口参数、
塔防冷却 300s。装机后落到 `%APPDATA%\dev.dota2helper2.app\constants\`，
**改 JSON 重启生效，不必重新编译**——上一个项目正是死于常数写死在代码里，版本一改就静默失效。

**快速模式的神符间隔与正常模式一致**（赏金 / 中路 / 智慧，2026-09-02 进游戏核对）。

**但莲花不同：快速模式是 1:30 首出、之后每 90 秒，正好是正常模式的一半**
（2026-09-08 实测）。2026-09-02 那次核对只看了神符没细核莲花，
把两者一并当成"与正常模式一致"，两张表因此长期写着同样的 180/180。

> 莲花**无法从录像验证**：`npc_dota_lotus_pool` 只有 2 个且全程静止（池子本体），
> 莲花本身不进 minimap，`generic_event` 的十八种消息里也没有莲花相关的。
> 只能进游戏看。
此前用 dump 反推（n=13 次赏金符拾取）无法区分 180s 与 240s，以实测为准。

## 模式判定

GSI 没有游戏模式字段。用 `player.gold_from_income / clock_time` 判定：
≈ 3.0 g/s = 快速，≈ 1.5 g/s = 正常（实测差整一倍，clock 60s 内可判定）。
判定完成前默认用快速表，判出来之后热切常数。

## 敌方塔防状态机

机制已被 3 局数据逐条验证，无反例。

**规则**：塔防冷却 300s；每队**第一座 T1、第一座 T2、第一座 T3、第一组近战兵营**被摧毁时，
该队塔防立即刷新（来源 Dota 2 Wiki，与全部实测数据吻合，含两个 15s / 76s 连开塔防的刁钻案例）。

**状态机**：per 敌方队伍维护 `last_use`（GLYPH_USED）与 4 个一次性刷新里程碑。
`ready = now >= last_use + 300s`，里程碑触发时直接置 ready。

**中途启动重建**：minimap 段推**双方所有塔**的存活状态
（`minimap_tower90` / `tower45` + team + 坐标），已消失的塔 = 已触发过的里程碑，可完整重建。
塔坐标→层级的映射做成静态表 `constants/towers.json`（从 dump 提取，双方各 11 座坐标已齐）。

> **空 minimap 不等于全塔阵亡**：判定"哪些塔没了"时，若 minimap 里一座塔都没有，
> 那是数据缺失而非全被推光，必须返回"未知"而不是 22 座全灰。

## 事件字段解码（实测确认）

| 事件 `generic_event.data.type` | 字段语义 |
|---|---|
| `CHAT_MESSAGE_GLYPH_USED` | `playerid1` = **使用方队伍**（2=天辉 3=夜魇，Dota 内部队伍常量） |
| `CHAT_MESSAGE_TOWER_KILL` | `value` = 击杀方队伍（丢塔方 = 对面）；`value3` = 塔层级 1~4；`value2` = 赏金（90/110/125/145） |
| `CHAT_MESSAGE_TOWER_DENY` | `value` = **丢塔方自己**（与 TOWER_KILL 相反，注意） |
| `CHAT_MESSAGE_BARRACKS_KILL` | `value` = 击杀方；`value2` = 155 近战 / 90 远程；`value3` = 兵营位置 bitmask |
| `CHAT_MESSAGE_BUYBACK` | `playerid1` = 买活玩家槽位（0-4 天辉 / 5-9 夜魇）。**双方都推**（实测己方 3 次敌方 2 次），买活是公示信息 |

**events 数组会在连续多包中重复推同一事件**，必须按 `(matchid, type, data.time)` 去重。

**队伍编号有两套，别混**：塔防/眼的 `team` 是 2/3；买活的 `playerid1` 和物品的 `purchaser`
是全局 0-9 槽位（夜魇要 +5）。

## 敌方买活追踪

per 敌方槽位记录 `last_buyback`，冷却 480s（进常数表）。

限制：玩家视角拿不到敌方英雄名，所以用 Dota 固定的**玩家槽位颜色点** + 倒计时显示。
只表示"冷却中 / 可用"，**无法得知对方有没有买活的钱**。

## 其余事件已全量盘点（2026-08-31）

物品购买 / 扫描 / 烟雾 / 排眼 / 瓶装符 / 信使等事件只推己方，无信息差价值；
击杀 / 阵亡 / 肉山 / 盾游戏原生已显示。**敌方买活是唯一有信息差且数据可得的增量。**

## 明确不做

- **敌方塔血量**：`buildings` 段只有己方，无数据。
- **队友 / 敌人的个体数据**：GSI 玩家视角不提供，无解。
